# Staging infrastructure (draft, not deployed)
Requires AWS credentials, Terraform >=1.6, an existing validated ACM certificate in the selected region, and control of staging DNS. Costs accrue for NAT, ALB, RDS and ECS. Single NAT and single-AZ RDS are staging tradeoffs, not production HA.

1. `terraform init`, `terraform validate`, `terraform plan -var='certificate_arn=YOUR_ACM_ARN'`. Review costs and permissions before applying. Use encrypted remote state with locking for team use; never commit state or tfvars with secrets.
2. Apply with enable_service=false. Build and push the Docker image to the ECR output using an immutable version tag; record its digest.
3. From an authorized temporary runner inside the VPC, use the RDS-managed master secret to create a restricted application database role and a separate migration role. Run `npm run migrate` and `npm run db:verify` on a new empty database using the migration role. Grant the application role only required DML and sequence privileges (including future migration review). Require TLS with the AWS RDS CA bundle. Store the application connection URI (URL-encoded password, sslmode=verify-full) in the database-url secret using the AWS console, not Terraform state. Do not use the master account for the web app. Runner and grants are manual and must be verified.
4. Apply with enable_service=true and image set to the ECR image digest URI. Create a staging DNS alias to the ALB using outputs. Confirm certificate matches APP_ORIGIN. Verify health and run smoke tests from an authorized client. All commerce flags remain false.
5. Configure alarms, WAF, restore drills and MFA before production. Do not switch the apex domain until acceptance. Secret rotation requires a new ECS deployment. The email worker is not scheduled by this stack.
